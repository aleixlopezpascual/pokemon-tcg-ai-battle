# Pre-submission evaluation methodology — what the community actually does

Companion to `discussion-intel-report.md` (that report covers scoring inconsistency and meta
signals broadly; this one is scoped narrowly to "how do competitors judge agent quality *before*
spending a submission," given the public leaderboard is documented elsewhere in this repo as
noisy for the first 24-48h).

## Sourcing method

Same as `discussion-intel-report.md`: Kaggle CLI's `topics` subcommand (no
`kaggle-competition-intel` MCP server installed here). Pulled all **204** discussion topics via
`kaggle competitions topics list pokemon-tcg-ai-battle --format json` (paginated via
`--page-token`, looped to an empty page), filtered titles against an evaluation-related keyword
list (evaluat/validat/benchmark/self-play/elo/rating/matchup/etc.), got **23 hits**, then pulled
full comment trees (`topics show <id>`) for the 6 most substantive: #712621, #717697, #715251,
#708617, #728243, #730823. Pulled 2026-08-07.

## No official reproducible benchmark exists

**#715251 — "Request for a reproducible evaluation loop beyond sparse live rating"** (kurikuri54,
2026-06-28): explicitly asked the host/community for a standardized reference evaluation, since
"an internal benchmark cannot reproduce or validate the official leaderboard signal when match
volume, opponent distribution, matchmaking conditions, and rating uncertainty are all controlled
by the host." The only reply (Dapp): "nothing is stopping you from creating your own internal
benchmarking system." No host response, no official alternative ever materialized. **Confirmed:
self-built local evaluation is the norm here, not a workaround for something better.**

## Six concrete community practices

1. **Local round-robin/ladder with TrueSkill or Elo as a local proxy for the Kaggle rating.**
   djschmit (#712621, 2026-06-29): ran a local ladder of 200 individual agents through 20,000
   matches, using TrueSkill as the ranking algorithm (paired matches based on current ranking),
   and explicitly tested how best-of-1 through best-of-9 match format affected ranking
   *stability* — snapshotting the leaderboard every 100 matches and measuring how much each
   agent's rank moved. Relevant if we ever want to tune how many games-per-matchup
   `src/local_eval.py` should run to get a stable win-rate read, not just a point estimate.

2. **Held-out validation split in the *opponent pool*, not just training data.** Jake (#717697,
   2026-07-04): "We currently run 6 learned agents and 3 public rule based agents in local
   mini-tournaments. With some held out from training data for validation purposes." — i.e.
   train/val discipline applied to which agents you evaluate against, so your eval signal isn't
   contaminated by opponents your own agent (or its training data) has already seen.

3. **Deck-diversity scaling in the local opponent pool, after diagnosing narrow-pool
   overfitting.** Jake (#717697, 2026-07-05): grew the local pool from 3 to 9 deck types after
   noticing local win-rate no longer predicted Kaggle performance — directly attributed the
   earlier divergence to too narrow a local matchup set. Our own `local_eval.py` roster is 4
   agents (random baseline + 3 of our own submissions) — worth weighing against this reported
   failure mode if local/Kaggle divergence shows up again.

4. **Deck-vs-deck matchup matrices via mass self-play** — but with a documented confound.
   ISAKA Tsuyoshi (#708617, 35 votes): shared ~15,000 self-play games across the 4 sample decks
   as a public matchup-matrix dataset. Countered directly by **#730823 — "Is That Matchup Table
   Measuring the Deck—or the Player? (Part 1)"** (Sumi): a matchup matrix generated by one agent
   playing both sides measures that agent's *skill differential* with each deck, not the decks'
   intrinsic strength — a matrix built from a weak Dragapult pilot understates Dragapult. Same
   caution applies to any matchup table we build or consume, including community-published ones.

5. **Replay-driven per-matchup failure analysis over trusting one aggregate win-rate number.**
   Abhyuday (#717697, 2026-07-04, to Dapp who was plateaued despite good local metrics): "replays
   are very important here. See what it's losing to by pulling replays and doing some data
   analysis... you can get very far with just 100 cards in your training [by studying losses]."
   Aggregate win rate tells you *that* something's wrong; replays tell you *what*.

6. **External sanity check via limitlesstcg.com real-tournament data — explicitly does not
   transfer to ranking.** Ryan Rumble (#717697) pointed to limitlesstcg.com for real high-placing
   decklists and strategy articles as a domain-knowledge source, but multiple threads (this one
   and `discussion-intel-report.md`'s meta-signal section) independently confirm human-tournament
   matchup data diverges meaningfully from the Kaggle-agent meta. Useful for rules/legal-play
   questions, not as an evaluation proxy.

## The load-bearing caveat: local eval frequently does not transfer to the real leaderboard

This is the single most-repeated, independently-corroborated point across #712621 and #717697:

- Zhenyu Zhang (#712621): "In our local round-robin / public-agent pool, one RL/ranker-style
  agent was the strongest candidate, but on the Kaggle leaderboard it only converged to around
  965. Meanwhile other variants that were not clearly better locally could reach much higher
  leaderboard scores."
- Dapp (#717697): "Internal leaderboard and metrics all point to a stronger local agent but then
  on Kaggle it doesn't translate."
- Jake (#717697): "Local round-robin play against our stable of agents usually correlates with
  better kaggle performance, but not always. 'Walls' of relatively low scoring agents with
  advantageous match ups... can be frustrating."

Nobody in these threads claims local evaluation alone is sufficient to pick a winner between two
comparable candidates — every report treats it as a **pre-submission sanity gate and diagnostic
tool**, with final ranking judgment deferred to the real (slow-converging, 24-48h-to-stabilize)
leaderboard. This independently corroborates this repo's own `baseline-comparison.md` calibration
finding about `src/local_eval.py`: it correctly flags obviously-weak candidates but inverts
fine-grained rankings between comparable-strength ones.

## Implication for our own workflow

`src/local_eval.py`'s 4-agent roster (random baseline + our 3 real submissions) is on the
narrower end of what the community reports as sufficient — Jake's 3→9 deck expansion and the
6-learned-agents-plus-3-rule-based pool in #717697 both sit meaningfully larger. If a future
candidate shows a strong local score that doesn't survive a real submission, narrow-pool
overfitting (finding 3 above) is a documented, independently-reported failure mode to check
first, not just bad luck. Similarly, djschmit's bo1-vs-bo-N stability experiment (finding 1)
suggests our own per-matchup game count is worth revisiting if local rankings ever look noisy
between comparable candidates — more games per matchup, not more candidates, may be the fix.
